## 4. 3戦略の定義

### 戦略① グリッドトレード

価格の上下に等間隔で買い・売り注文の「網」を張り、価格が動くたびに自動で売買が成立する仕組み。価格を予測しなくてよく、上下どちらに動いても利益が積み上がる。

**パラメータ**

| 項目 | 値 | 備考 |
|------|-----|------|
| 価格レンジ | 1,150万〜1,400万円 | 現在価格の前後約10% |
| グリッド幅 | 50万円ごと | 5段階 ※自動最適化により変更される可能性あり |
| 1回の売買量 | 0.001 BTC（約1.3万円） | 保有量に応じて調整 |
| 想定取引回数 | 月10〜20回程度 | 相場の動き次第 |

**ロジック**
```
前回約定価格より50万円以上下落 → 買いシグナル（約定時のみ基準価格を更新）
前回約定価格より50万円以上上昇 → 売りシグナル（約定時のみ基準価格を更新）
変化が50万円未満             → 待機（基準価格は保持）
```

> **注意**: 待機時に基準価格を更新すると小刻みな価格変動でリセットされ、
> グリッドが機能しなくなるバグが初期実装に存在した。2026年5月24日に修正済み。

**弱点**: 一方向に強く動くトレンド相場では損失が拡大する可能性あり

---

### 戦略② 移動平均クロス

短期移動平均線が長期移動平均線を上抜けたら買い、下抜けたら売る。トレンドに乗る戦略。

**パラメータ**

| 項目 | 値 | 備考 |
|------|-----|------|
| 短期移動平均 | 6期間（6時間） | 直近6回の取得価格の平均 |
| 長期移動平均 | 24期間（24時間） | 直近24回の取得価格の平均 |
| 1回の売買量 | 0.001 BTC（約1.3万円） | 同上 |
| 最低データ蓄積期間 | 24時間 | 長期MAが計算できるまで待機 |

**ロジック**
```
短期MA > 長期MA（かつ前回は短期MA ≤ 長期MA） → 買いシグナル（ゴールデンクロス）
短期MA < 長期MA（かつ前回は短期MA ≥ 長期MA） → 売りシグナル（デッドクロス）
それ以外                                     → 待機
```

**弱点**: レンジ相場ではだまし（偽シグナル）が多発してコスト負けする

---

### 戦略③ 複合（グリッド＋移動平均）

移動平均でレンジ相場かトレンド相場かを判定し、相場に応じて戦略を切り替える。

**ロジック**
```
短期MA ≈ 長期MA（差が1%以内） → レンジ相場と判定 → グリッドトレードを実行
短期MAと長期MAに1%超の乖離    → トレンド相場と判定 → グリッドを停止・待機
```

**期待効果**: グリッドの弱点（トレンド相場での損失）を移動平均で補う

## 5. 共通リスク管理ルール

| ルール | 設定値 | 理由 |
|--------|--------|------|
| 損切りライン | BTC価格が1,100万円を下回ったら全戦略停止 | 元本割れ拡大防止 |
| 1回の最大売買量 | 0.001 BTC | 約1.3万円、実験枠5万円の約25% |
| 連続シグナル制限 | 同方向のシグナルは1時間以内に重複しない | 過剰取引防止 |

## 6. ログフォーマット

### `logs/simulation_log.csv`

```csv
timestamp,btc_price_jpy,strategy,signal,simulated_action,simulated_qty_btc,cumulative_pnl_jpy,ma_short,ma_long,notes
2026-05-14 06:00:00,12900000,grid,buy,would_buy,0.001,0,,,価格がグリッドライン下抜け
2026-05-14 06:00:00,12900000,ma,hold,none,0,0,12850000,12920000,クロスなし
2026-05-14 06:00:00,12900000,combined,hold,none,0,0,12850000,12920000,レンジ判定・グリッド待機
```

**カラム定義**

| カラム | 内容 |
|--------|------|
| timestamp | 実行日時（JST） |
| btc_price_jpy | BTC価格（円） |
| strategy | 戦略名（grid / ma / combined） |
| signal | シグナル（buy / sell / hold） |
| simulated_action | 仮想的に取った行動 |
| simulated_qty_btc | 仮想売買量 |
| cumulative_pnl_jpy | 累計損益（円） |
| ma_short | 短期移動平均 |
| ma_long | 長期移動平均 |
| notes | 備考 |

### `logs/optimizer_log.md`

毎週月曜の自動最適化実行ごとに追記される変更履歴。
Claude APIによる分析内容・変更理由・変更前後のコード行数を記録する。

## 7. 月次評価基準

1ヶ月後に以下の指標で3戦略を比較する。

| 指標 | 内容 |
|------|------|
| 累計損益（円） | シミュレーション上の利益/損失の合計 |
| 取引回数 | 多すぎると手数料負けリスク |
| 勝率 | 利益が出た取引の割合 |
| 最大ドローダウン | 最も大きく含み損を抱えた時の金額 |
| 手数料換算コスト | 取引回数 × 推定手数料（Taker: 0.05%） |

**採用基準**: 累計損益がプラスかつ手数料換算後も黒字の戦略を本番採用

## 10. 自動最適化（戦略セルフチューニング）

### 概要

シミュレーション期間中、Claude APIがログを定期的に分析してロジックを自動改善する。
改善内容はコミット履歴と`optimizer_log.md`で追跡可能。

### 構成ファイル

| ファイル | 役割 |
|----------|------|
| `src/optimizer.py` | 最適化スクリプト本体 |
| `.github/workflows/optimize.yml` | 週次実行ワークフロー |
| `logs/optimizer_log.md` | 変更履歴（自動追記） |
| `docs/design_constraints.md` | 変更禁止ルール一覧（Haikuに渡す制約） |

### 実行スケジュール

- 毎週月曜 06:30 JST（通常シミュレーション直後）
- `workflow_dispatch`で手動実行も可能

### 使用モデルとコスト

| 項目 | 内容 |
|------|------|
| モデル | Claude Haiku 4.5（`claude-haiku-4-5-20251001`） |
| 料金 | $1.00/$5.00 per MTok（入力/出力） |
| 月4回の推定コスト | 約$0.10〜0.15/月 |
| GitHub Actions追加使用量 | 約8分/月（影響なし） |

### 最適化の方針

- バグ修正を最優先（誤動作しているロジックを直す）
- パラメータ調整は根拠がある場合のみ実施
- 3戦略の基本的な枠組みは変えない
- リスク管理ルール（損切りライン等）は変えない

### 必要なGitHub Secrets

| Secret名 | 用途 |
|----------|------|
| `ANTHROPIC_API_KEY` | Claude API認証（2026年5月24日登録済み） |
